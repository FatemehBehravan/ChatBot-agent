# ایجنت دستیار تحویل الوپیک — تسک فنی

> 🇬🇧 English version: [README.md](README.md)

## اجرای مرحله ۱ (stub)

مرحله‌ی ۱ یک API پایتون است. بدون کلید API و بدون مدل لوکال بالا می‌آید. فایل `.env` اختیاری است.

```bash
docker compose up --build
curl http://localhost:8000/health
curl -s -X POST http://localhost:8000/v1/chat -H "Content-Type: application/json" -d "{\"message\":\"سلام\"}"
```

در PowerShell از `curl.exe` استفاده کنید. ادامه‌ی گفتگو با `session_id` برگشتی است و `user_id` پیش‌فرض `u-anon` است. تست آفلاین داخل ایمیج، بدون شبکه:

```bash
docker run --rm --network none -v "./data:/app/data:ro" alopeyk-agent-app python -m pytest -q
```

جزئیات اجرا، از جمله پروفایل اختیاری Ollama، در [README.md](README.md) آمده است. `APP_PROVIDER` را تا مرحله‌های بعد روی `stub` نگه دارید. صفحهٔ چت روی [http://localhost:8000/](http://localhost:8000/) است.

## ۱. زمینه

[الوپیک](https://alopeyk.com/) یک پلتفرم تحویل درخواستی (on-demand) است: مشتری یک پیک (موتور، ماشین یا وانت) درخواست می‌کند تا مرسوله، مدارک، غذا و موارد دیگر را داخل شهر یا بین شهرها جابه‌جا کند. این شرکت محتوای آموزشی و راهنمای زیادی (وبلاگ و صفحات آموزش/راهنما) منتشر می‌کند و یک پایگاه‌داده‌ی عملیاتی بزرگ از سفارش‌ها دارد.

وظیفه‌ی شما طراحی و پیاده‌سازی بک‌اند یک **ایجنت دستیار چت** برای این حوزه است. ایجنت باید از دو نوع منبع پاسخ بدهد — یک **پایگاه دانش** ساخته‌شده از محتوای عمومی وبلاگ/آموزش شرکت و یک **اسنپ‌شات از دیتابیس سفارش‌ها** — و از طریق ابزارها چند اقدام کنترل‌شده انجام دهد؛ در عین حال در شرایط واقعی درست رفتار کند: محدودیت context window، سقف توکن، محدودیت‌های دسترسی بر اساس نقش، استفاده‌ی همزمان از مدل لوکال و API و داده‌های غیرقابل‌اعتماد.

نمونه پرسش‌هایی که دستیار باید پوشش دهد:

- «برای مسیر ۵ کیلومتری با موتور در تهران، معمولاً تحویل چقدر طول می‌کشد؟» ← پاسخ **آماری از روی اسنپ‌شات سفارش‌ها**، همراه با تعداد نمونه، بازه‌ی معمول و محدودیت‌ها (نه یک وعده‌ی ساختگی).
- «سفارش A-246001 من کجاست؟» ← پاسخ از جدول سفارش‌ها، فقط اگر سفارش متعلق به مشتریِ واردشده باشد.
- «اقلام شکستنی را چطور بسته‌بندی کنم؟» ← پاسخ از **پایگاه دانش همراه با ارجاع به منبع**، یا «پیدا نشد» صادقانه.
- «برای سفارش دیرکرده‌ام تیکت پشتیبانی ثبت کن.» ← اقدام نوشتنی که تأیید صریح می‌خواهد.

## ۲. چه چیزی می‌سازید

یک ایجنت چت داکرایز‌شده (HTTP API و/یا CLI، به‌علاوه‌ی UI اختیاری) که:

۱. گفتگوی چندنوبتی به فارسی.
۲. از ابزارها روی دیتابیس سفارش‌ها و یک ایندکس بازیابی از اسناد پایگاه دانش استفاده می‌کند.
۳. **همزمان با یک مدل لوکال و یک مدل API** کار می‌کند و انتخاب بین آن‌ها با سیاست مسیریابی (routing) صریح و قابل‌تنظیم انجام می‌شود.
۴. کنترل دسترسی مبتنی بر نقش را **در کد** اعمال می‌کند، نه فقط در پرامپت.
۵. context window و محدودیت توکن را آگاهانه مدیریت می‌کند.
۶. قابل‌اندازه‌گیری است: همراه با تست‌های آفلاین و ابزار ارزیابی (eval) تحویل می‌شود.
۷. با `docker compose up` به‌صورت سرتاسری اجرا می‌شود.

## ۳. قواعد کلی

- **زبان، پلتفرم، فریمورک و دیتابیس آزاد است** (SQLite، PostgreSQL، DuckDB و… و هر روش بازیابی کلیدواژه‌ای یا برداری). هر فریمورک ایجنتی (LangGraph، LlamaIndex، SDK خام یا هیچ‌کدام) پذیرفته است؛ دلیل انتخاب‌ها را در سند تحویل بنویسید.
- استفاده از دستیارهای کدنویسی هوش مصنوعی مجاز است. محل و نحوه‌ی استفاده را اعلام کنید و آماده‌ی توضیح تک‌تک خطوط تحویلی باشید.
- هیچ secret ای در ریپو یا ایمیج‌های Docker نباشد. فایل `.env.example` بگذارید؛ کلیدهای واقعی فقط در متغیرهای محیطی باشند.
- مجموعه‌ی تست‌ها باید **آفلاین** پاس شود (بدون شبکه و بدون کلید واقعی) و از مدل stub و مجموعه‌ی fixture در `data/knowledge/seed/` استفاده کند.
- اسنپ‌شات سفارش‌ها در `data/` **مصنوعی (synthetic)** است و برای این تسک تولید شده؛ داده‌ی واقعی شرکت نیست.
- محتوای پایگاه دانش را **کد ingestion شما** از وب‌سایت جمع‌آوری می‌کند و کل آن در ریپو commit نمی‌شود. به `robots.txt`، شرایط استفاده و نرخ درخواست معقول احترام بگذارید؛ برای هر سند آدرس منبع و تاریخ دریافت را ذخیره کنید. کد ingestion و حداکثر یک نمونه‌ی کوچک را commit کنید.
- «اکنون» مرجع برای همه‌ی داده‌ها و ارزیابی‌ها: `2026-11-14T10:00:00+03:30`.

## ۴. مدل‌ها

### مدل لوکال
هر مدلی که روی سیستم خودتان از طریق endpoint سازگار با OpenAI سرو شود (Ollama، سرور llama.cpp، LM Studio، vLLM و…). مدلی را انتخاب کنید که با سخت‌افزارتان سازگار باشد، tool/function calling را پشتیبانی کند و فارسی را قابل‌قبول بفهمد؛ خانواده‌های قابل‌امتحان: Qwen2.5-Instruct، Llama 3.1/3.2 Instruct، Mistral/Mistral-Nemo، Gemma و Phi. آدرس OpenAI-compatible در Ollama معمولاً `http://localhost:11434/v1` است (از داخل کانتینر: `http://host.docker.internal:11434/v1` یا با پروفایل compose بخش ۸: `http://ollama:11434/v1`).

### مدل API
هر endpoint سازگار با OpenAI. برای نزدیک به صفر نگه‌داشتن هزینه می‌توانید از این‌ها استفاده کنید:

- اعتبار رایگان/آزمایشی حساب مستقیم یک ارائه‌دهنده، در صورتی که در دسترس شما باشد (مثلاً OpenAI)، یا
- یک gateway سازگار با OpenAI که اعتبار اولیه می‌دهد، مانند **AvalAI (اول ای‌آی)** یا **BoxAPI (باکس API)** یا سرویس مشابه.

شرایط و میزان اعتبار رایگان در طول زمان تغییر می‌کند؛ صفحه‌ی فعلی ارائه‌دهنده را بررسی کنید. آدرس پایه (base URL)، کلید و نام مدل را در متغیرهای محیطی نگه دارید تا تعویض ارائه‌دهنده بدون تغییر کد ممکن باشد. یک مدل ارزان انتخاب کنید و از محافظ‌های بودجه‌ای که در مرحله‌ی ۶ می‌سازید استفاده کنید.

### Embedding (در صورت استفاده از جستجوی معنایی)
یک مدل embedding لوکال (مثلاً از طریق Ollama) یا API — به انتخاب شما. پشتیبانی از فارسی مهم است؛ انتخاب را توجیه کنید. بازیابی کلیدواژه‌ای/BM25 هم پذیرفته است، به شرط اینکه روی پرسش‌های ارزیابی کارایی‌اش را نشان دهید.

## ۷. UI اختیاری

UI **الزامی نیست** — CLI یا HTTP API کافی است. اگر UI می‌سازید، چند گزینه‌ی سریع:

- **Streamlit** — سریع‌ترین در پایتون (`st.chat_message`، `st.chat_input`، استریم با `st.write_stream`)؛ برای دمو عالی است، با یک سایدبار برای تعویض کاربر واردشده.
- **Chainlit** — مخصوص چت؛ نمایش مراحل tool call و استریم را به‌صورت آماده دارد.
- **Gradio** با `ChatInterface` — کد بسیار کم.
- یک صفحه‌ی وب ساده که API شما را صدا بزند (با هر فریمورکی).

مواردی که نمایش‌شان در UI ارزشمند است (همه اختیاری): مدلی که هر نوبت را پاسخ داده، مصرف توکن، tool callها، ارجاع به منابع و یک سوییچر کاربر فقط برای توسعه. برای فارسی، `direction: rtl` و تراز راست را برای حباب‌های چت تنظیم کنید و از یک فونت فارسی که به‌صورت محلی همراه پروژه است استفاده کنید (UI نباید برای نمایش به اینترنت نیاز داشته باشد).

## ۸. داکرایز (الزامی)

- `docker compose up --build` کل سیستم را بالا می‌آورد (API ایجنت، دیتابیس اگر جداست، UI اگر دارید) و روش اصلی مستند اجرای پروژه است.
- یک `Dockerfile` با build چندمرحله‌ای، نسخه‌ی پین‌شده‌ی ایمیج پایه، کاربر runtime غیر root و فایل `.dockerignore`.
- پیکربندی فقط از طریق متغیرهای محیطی / `.env`؛ **هیچ secret ای داخل ایمیج نباشد**؛ state (دیتابیس، نشست‌ها، ایندکس بازیابی) روی volumeهای نام‌دار.
- healthcheck و ترتیب درست بالا آمدن سرویس‌ها (`depends_on` با شرط سلامت)؛ بارگذاری داده و ساخت ایندکس **idempotent** باشد و خودکار یا با یک دستور مستند یک‌خطی اجرا شود.
- مدل لوکال باید از داخل کانتینر قابل‌دسترس باشد: یا سرور روی میزبان از طریق `host.docker.internal` (compose اولیه مپینگ `host-gateway` لینوکس را اضافه کرده)، یا پروفایل `local-llm` در compose با کانتینر Ollama و یک مرحله‌ی مستند دریافت مدل.
- تست‌ها باید **داخل کانتینر** با یک دستور مستند اجرا شوند و با شبکه‌ی غیرفعال هم پاس شوند.
- یک `docker-compose.yml` اولیه ارائه شده؛ آن را کامل و متناسب کنید.

مراحل را به ترتیب انجام دهید. هر مرحله را در یک pull request جداگانه یا یک commit تگ‌شده (`stage-1` تا `stage-11`) تحویل دهید تا روند پیشرفت در تاریخچه دیده شود. مرحله زمانی کامل است که همه‌ی موارد پذیرش آن تیک بخورد.

### مرحله ۱ — اسکلت، پیکربندی و کانتینر
- [x] ساختار پروژه طبق بخش ۶ (یا نسخه‌ی مستند‌شده‌ی دیگر).
- [x] پیکربندی تایپ‌دار از `config/*.yaml` و متغیرهای محیطی؛ پیکربندی نامعتبر با پیام روشن همان ابتدا شکست بخورد (fail fast).
- [x] `Dockerfile`، `.dockerignore` و `docker-compose.yml` کامل‌شده مطابق بخش ۸.
- [x] با کلون تازه و فقط با `docker compose up --build` و README بتوان با مدل stub چت کرد.

### مرحله ۲ — لایه‌ی ارائه‌دهنده‌ی LLM
- [x] یک interface مشترک: chat completion، streaming اختیاری، شمارش توکن، قابلیت‌های اعلام‌شده (context window، حداکثر خروجی، پشتیبانی از tool calling).

- [x] تعویض ارائه‌دهنده فقط با تغییر پیکربندی ممکن باشد.

- [x] فایل‌های CSV اسنپ‌شات با یک loader ایدمپوتنت در دیتابیس انتخابی شما بارگذاری شوند؛ ایندکس‌ها کوئری‌های موردنیاز را کارا پشتیبانی کنند.

- [x] کیفیت بازیابی روی یک مجموعه پرسش کوچک که خودتان می‌نویسید سنجیده و نرخ موفقیت (hit rate) در سند تحویل گزارش شود.
